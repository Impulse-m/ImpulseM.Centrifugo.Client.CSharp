# Changelog

## Unreleased

* Token exchange: `CentrifugeClientOptions.TokenExchange` lets the client obtain and renew its connection token over the connection, from a refresh token the application persists through a `CentrifugeTokenExchange` (`Load`, `Store`, `ExchangeAsync`). The anonymous connect is completed by an exchange on the same socket before the connection is reported connected, and every rotated refresh token is stored before its access token is used. Exclusive with `GetToken`: a client created with both throws `CentrifugeConfigurationException`.
* With a token exchange the connection token is renewed at a random moment between 70% and 90% of its TTL, so connections which started together spread their renewals. `CentrifugeTokenExchange.EarlyRenewal` widens the window to 60% to 90%. Without a token exchange the refresh timer runs at the full TTL.
* Token exchange: `CentrifugeTokenExchange.RefusalTypes` names the server error app types that mean a refused refresh token. `GraceSeconds` and the `CentrifugeTokenExchangeResult` constructor carry the issuer's grace in seconds. A refused refresh token is presented again once, inside the grace horizon, and a second refusal of it ends the session. A refusal is reported as `CentrifugeTokenExchangeRefusedException` when its app type is listed.
* Token exchange: a rotated refresh token is stored only while the storage still holds the one the exchange used, so a logout during an exchange is not undone. `Load()` may throw `CentrifugeUnauthorizedException`: that ends the session, at bootstrap and at renewal. Any other exception is reported and retried with backoff.
* Token exchange failures are reported through the `Error` event: `connectToken` (code 5) on bootstrap and `refreshToken` (code 6) on renewal. A dead session disconnects with code 1 (`unauthorized`) and does not reconnect.
* Publish debouncing: when the server returns a publish debounce window in the subscribe result, `Subscription.PublishAsync` sends the first value at once and coalesces the rest of the window into the latest one. Pending data is dropped on unsubscribe and disconnect. The window has no maximum except the 32-bit limit of its length.
* Channel compaction is offered on every subscribe and negotiated automatically when the server allows it.
* Connection identity: the `Auth` event reports the user and auth class of the connection on every connect, and when a refresh changes them. `CentrifugeAuthEventArgs` carries `User` and `AuthClass` only.
* `CentrifugeClient.RefreshAsync(token, cancellationToken)` refreshes the connection token on demand. An error is reported to the caller unchanged, and keeps the connection and its identity. At most 32 refreshes are in progress; a refresh beyond that fails with `CentrifugeErrorCodes.LimitExceeded` (16). A refresh with the token of a pending refresh shares its command. A refresh made while disconnected sets the token of the next connect, and the previous token is restored when the server refuses that refresh.
* A timer token fetch or refresh that fails is retried with a delay which doubles per failure in a row, up to `CentrifugeClientOptions.TokenRetryCap`. By default the cap is 5 minutes. A success restarts the delay.
* Deviation from upstream: a timer refresh refused with 103 keeps the connection and its identity, and is not retried. A timer refresh refused with 109 is retried with a fresh token, instead of disconnecting. Other codes behave as upstream.
* `CentrifugeClientOptions.Instance` sets the connection instance, a secret the application supplies. With it, rpc calls on a server which confirms RPC options are exactly-once: each call carries a `msg_id`, is kept across a reconnect and sent again with the retransmit flag. Without an instance calls are plain, as before.
* `CentrifugeClient.RpcCall` returns a `CentrifugeRpcCall` whose `Cancel()` cancels the call on the server when the connection carries the cancel. `CentrifugeRpcResult.Cached` tells whether the server answered from its record.
* A call made with `RpcCall` or with `CentrifugeRpcOptions` that is lost with its connection fails with the same code, message and cause as the plain call, as a `CentrifugeException`. A token cancelled before such a call fails it with `Cancelled` at once, and nothing is sent. The overload with a token and no options keeps its plain failures.
* `CentrifugeClientOptions.MaxPendingRpc` (32 by default) bounds the unsettled calls of a client with an instance. A call beyond it fails at once with `CentrifugeErrorCodes.LimitExceeded` and is not sent.
* Error codes 15 (`Unsupported`), 16 (`LimitExceeded`), 17 (`Cancelled`) and 18 (`RedirectFailed`) are client-local: a server never sends them.
* A refused rpc call is sent again when the server sets the `x-centrifugo-retry` metadata key: `new_msg_id` after a re-sync of the clock, with a new `msg_id`, at most twice; `later` after a random delay (full jitter) with the same `msg_id`, at most three times. The call's deadline bounds the attempts.
* `CentrifugeException` carries `AppCode`, `AppType` and `Metadata` of the server error.
* An rpc call cancelled before it was sent is rejected with `Cancelled` on every connection. A call with an instance whose `msg_id` was never written is rejected with `Cancelled` when the client closes or disconnects for good.
* RPC options: `client.RpcAsync(method, data, options)` takes a `CentrifugeRpcOptions` whose headers go with that one call. The connect reply confirms the capability, which `Capabilities.RpcOptionsSupported` reports. Without it, a call with headers fails locally with `Unsupported`.
* `CentrifugeRpcPool` sends large-payload rpc calls over several plain connections per endpoint, with a per-connection window, a bounded queue, resends for a lost connection, a later refusal and a server reroute, a server-issued affinity header, and a redirect hook which fetches the bytes over HTTP. A connection closed for a frame over its size limit settles its calls without a resend.
* `CentrifugeRpcPool` follows no redirect of a fetch: a 3xx answer fails the fetch with `RedirectFailed`. Its `CentrifugeRpcPoolOptions.TokenFrom` takes the token from the main client, which renews itself when a pool connection is refused its token.
* `CentrifugeRpcPool.Close()` settles the calls waiting for a connection with `Cancelled`, and the calls on the wire and the redirect fetches with `IOException`.
* A failure thrown by an rpc callback or by an event handler is reported to the `Error` event as a `CentrifugeUnclassifiedException` which wraps it, as upstream reports it.
* A subscribe reply with code 109 and no `GetToken` in `CentrifugeSubscriptionOptions` unsubscribes the subscription as unauthorized, and reports a configuration error to the `Error` event.
* State invalidation keeps a static token. The subscription token is cleared on code 2502 (an unsubscribe push) and on code 3014 (a disconnect), and the connection token on 3014, only when a `GetToken` is set.
* A delta publication which arrives with no base to apply it to is an error: it is reported to the `Error` event as a `CentrifugeUnclassifiedException`, and the client disconnects with code 2 (`bad protocol`).
* An unsubscribe whose reply carries an error, or which times out while the client is connected, disconnects the client with reason `unsubscribe error` and reconnects it, so the server starts from a clean state.
* The fork's `Fossil.cs` header carries the full BSD 2-Clause notice. The code is unchanged.
* Package: the NuGet package id is `ImpulseM.Centrifuge`. The code namespace stays `Centrifugal.Centrifuge`.
